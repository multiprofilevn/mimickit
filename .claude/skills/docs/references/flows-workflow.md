# Flows Workflow — shared mechanism

This file is the **shared diagram-generation mechanism** used by the per-output flow workflows. It
is NOT invoked directly and has **no `--preview` opt-in** of its own. Its callers each own detection
+ file template; they reference this file for the mechanics: relevance gates, language rules,
mermaid label safety, the validation gate, the git-diff staleness check, and fallbacks.

## Base-path parameter

The mechanism operates against a configurable **base-path** — the caller decides where files land
and how they are keyed:

| Caller | Base-path | File pattern | Keyed by | Detection / template |
|--------|-----------|--------------|----------|----------------------|
| `docs services` | `docs/services/<svc>/` | `docs/services/<svc>/flows.md` | module name | `services-workflow.md` |
| `docs flows` | `docs/flows/` | `docs/flows/<process>.md` | business-process name | `business-flows-workflow.md` |

All rules below — relevance gates, language, mermaid safety, validation gate, staleness check,
fallback, node limit — apply unchanged regardless of base-path. Do NOT fork this logic in a caller.

> **Deprecated caller:** `docs init/update --preview` previously generated per-domain
> `docs/flows/<domain>-flow.md` here. That output was removed (it duplicated
> `docs/services/<svc>/flows.md`). `docs/flows/` is now owned by `docs flows` (business processes).
> The brainstorm/plan `--preview` (inline diagram in `plan.md`) is a different mechanism entirely
> and does not use this file.

## Relevance gates — additional diagrams

The caller's own file template defines the frontmatter (`sources` + `commit`) and the primary
flowchart. Beyond that primary flowchart, add these extra diagrams ONLY when their gate is met:

| Diagram type | Add ONLY IF |
|---|---|
| Sequence diagram | Flow crosses ≥ 2 distinct services or actors (e.g. API → worker → external service) |
| State diagram | A core entity in the domain has ≥ 3 distinct lifecycle states |
| ER snippet | Domain owns ≥ 3 directly related entities/models |

If a gate is not met, **omit that section entirely** — do not add a placeholder or comment.

All diagrams: inline ` ```mermaid ` blocks, ≤ 12 nodes each, written as text (not generated by a tool).

### Language (MANDATORY)

All human-facing prose and diagram labels in these flow files are written in **Vietnamese (Tiếng
Việt)**: the heading, the summary paragraph, edge labels and node text in every mermaid block,
sequence/state/ER descriptions. Keep in **English**: node IDs (`A`, `B2`, `HASH`), code identifiers,
file paths, mermaid keywords (`flowchart TD`, `stateDiagram-v2`), and technical proper nouns (JWT,
S3, Redis, API). This applies to both `docs/flows/<process>.md` and `docs/services/<svc>/flows.md`.

(`reference.md` is the exception — it stays English, see `services-workflow.md`: AI-facing, grep-optimised.)

---

### Mermaid label safety (MANDATORY — prevents parse errors)

Unquoted special characters in labels are the #1 cause of "Parse error on line N" that makes the
whole diagram fail to render. Follow these rules with **zero exceptions**:

1. **Always wrap EVERY edge label and EVERY node text in double quotes.** Do not rely on "this label
   looks simple". Quote unconditionally — it is always valid and removes the entire error class.
   - Edge label: `A -->|"label text"| B` (NOT `A -->|label text| B`)
   - Node text: `B["node text"]`, `C{"decision text"}`, `D("rounded text")`
2. **Quotes must be balanced.** Every label has exactly one opening `"` and one closing `"`. The
   classic bug is a trailing quote with no opening one — e.g. `-->|Fail / No Service / C3 / C7"|`
   parses as broken. Correct: `-->|"Fail / No Service / C3 / C7"|`.
3. **Characters that REQUIRE quoting** (and will break unquoted labels): `/`  `(` `)` `{` `}` `[` `]`
   `|` `#` `<` `>` `:` `;` `,` `.` `&` `"` `'`, the literal string `<br/>`, and any `${...}` token.
   Since rule 1 already quotes everything, this list is just the "why".
4. **Inside a quoted label, do NOT use a raw `"`.** Use `&quot;` (or `#quot;`) for a literal double
   quote, and `<br/>` only for line breaks (it is safe inside quotes).
5. **Node IDs stay unquoted and ASCII** (`A`, `B2`, `AA`) — only the *display text* is quoted.
6. **Node bracket shapes must match — opener and closer are the SAME shape.** This is a second,
   distinct error class (different from quoting). A decision/diamond node opens with `{` and MUST
   close with `}`; a rectangle opens `[` closes `]`; rounded opens `(` closes `)`. Compound shapes
   mirror exactly: stadium `(["…"])`, subroutine `[["…"]]`, cylinder `[("…")]`, hexagon `{{"…"}}`,
   circle `(("…"))`. NEVER mix shapes:
   - ❌ `A6{"All gates<br/>pass?"]` — opened `{`, closed `]` → `Expecting 'DIAMOND_STOP' … got 'SQE'`.
   - ✅ `A6{"All gates<br/>pass?"}`.
   A label ending in `?` is almost always a decision node → make sure BOTH brackets are `{` and `}`.

**Self-check before writing the file (do this for every ```mermaid block):**
- Scan each line: does every `|...|` edge label and every `[...]`/`{...}`/`(...)` node body start
  AND end with `"`? If any label contains a char from rule 3 but is missing a quote → fix it.
- Count `"` per label line — must be even. An odd count = unbalanced = parse error.
- For each flowchart node, confirm the closing bracket(s) are the SAME shape as the opening
  bracket(s) — never `{…]`, `[…}`, `(…]`, etc.
- If unsure, re-read against the `mermaidjs-v11` reference (syntax check only — never invoke it as a
  generator).

**Validation gate (MANDATORY — run after writing each flow file):**

After writing `flows.md` / `<process>.md`, run the deterministic checker and fix anything it
reports before considering the file done:

```bash
node .claude/skills/docs/scripts/validate-mermaid.cjs <path-to-written-file>
```

It flags the two recurring defect classes (unbalanced quotes, mismatched node brackets) with exact
`file:line` locations and exits non-zero on any problem. Loop: run → if non-zero, fix the reported
lines → re-run → only proceed when it prints `OK`. This catches what self-review misses (the
generator and the reviewer are the same model). Path is relative to the project root where the skill
runs; if the script is absent in that project, fall back to the manual self-check above.

## Commit hash

Before writing any file, capture the HEAD commit:

```
git rev-parse HEAD
```

Use the full hash as the `commit` field in each file's frontmatter. If the repo has no commits
(freshly initialised), use the string `"initial"` and note it in the turn.

## Update mode

### Step 1: Staleness check (per existing flow file)

For each file in `<base-path>/` (caller-supplied — e.g. `docs/flows/` for `docs flows`,
`docs/services/<svc>/` for `docs services`):

1. Read its frontmatter to extract `commit` and `sources`.
2. Run:
   ```
   git diff --name-only <commit>..HEAD -- <sources>
   ```
3. Interpret output:
   - **Non-empty** → one or more source files changed since the diagram was drawn.
     Regenerate the entire file (summary + all diagrams) and update `commit` to HEAD.
   - **Empty** → no source changes. Skip this file — do not rewrite it.

### Step 2: New items

Compare the caller's current detection list (services → modules; flows → business processes)
against existing `<base-path>/` files. Any item without a corresponding file → create it (same
template the caller uses on init).

### Step 3: Removed sources

If a flow file's `sources` paths no longer exist in the repo:
→ **Warn the user** in the turn output: which file, which missing paths.
→ **Do NOT auto-delete** the flow file — the user decides whether to remove or remap sources.

## Fallbacks (git not available or unreliable)

Trigger any of these conditions → fall back to full regeneration of all flow files:

| Condition | Detection |
|---|---|
| Not a git repo | `git rev-parse HEAD` exits non-zero |
| Shallow clone | `git rev-parse --is-shallow-repository` returns `true` or exits non-zero (old git) |
| `commit` field in frontmatter is `"initial"` or missing | Parse frontmatter |
| Unknown / corrupt commit hash | `git cat-file -t <commit>` exits non-zero |

Fallback behaviour:
1. Warn the user (one line, state which condition triggered).
2. Regenerate every flow file from scratch using current scout context.
3. Set `commit` to the current HEAD (or `"initial"` if no commits exist).

## Output location

**docs flows mode:** `docs/flows/<process>.md` (kebab-case business-process name).
The `docs/flows/` directory is created on first write if it does not exist.

**docs services mode:** `docs/services/<svc>/flows.md` — base-path is `docs/services/<svc>/`.
The `docs/services/<svc>/` directory is created on first write if it does not exist.

The Phase 3 size check in the init/update workflows includes both:
- `docs/flows/*.md` (business-process files, written by `docs flows`)
- `docs/services/*/flows.md` (per-service files, written by `docs services`)
